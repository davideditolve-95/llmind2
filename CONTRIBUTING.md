# Contributing / Linee Guida di Contributo

## Italiano

### Filosofia

LLMind2 e un progetto di ricerca scientifica applicata. Contribuire significa migliorare non solo il software, ma anche la qualita del suo uso come infrastruttura sperimentale. Ogni contributo dovrebbe quindi aumentare almeno una di queste dimensioni:

- affidabilita del prodotto
- chiarezza del codice
- riproducibilita degli esperimenti
- qualita della documentazione
- capacita di collaborazione tra agenti e persone

### Prima di iniziare

Leggere almeno:

- `README.md`
- `AGENTS.md`
- `docs/00-project-overview.md`
- `docs/01-multi-agent-playbook.md`
- `docs/09-api-dataflow-map.md`

### Regole pratiche

- evitare modifiche distruttive non richieste
- se si cambia il comportamento, aggiornare anche la documentazione
- se si toccano benchmark o prompt, esplicitare l'impatto sulla comparabilita dei risultati
- distinguere sempre fix prodotto da cambiamento metodologico

### Pull request o handoff interni

Ogni contributo dovrebbe chiarire:

- problema affrontato
- soluzione adottata
- file toccati
- rischi residui
- verifiche eseguite

### Standard per documentazione

La documentazione del progetto e bilingue. Quando si aggiungono documenti strategici o manuali, mantenere:

- sezione in italiano
- sezione in inglese
- tono tecnico, formale e adatto a uso accademico

## English

### Philosophy

LLMind2 is a scientific applied-research project. Contributing means improving not only the software, but also its quality as experimental infrastructure. Every contribution should strengthen at least one of the following:

- product reliability
- code clarity
- experimental reproducibility
- documentation quality
- collaboration between agents and people

### Before starting

Read at least:

- `README.md`
- `AGENTS.md`
- `docs/00-project-overview.md`
- `docs/01-multi-agent-playbook.md`
- `docs/09-api-dataflow-map.md`

### Practical rules

- avoid destructive changes unless explicitly requested
- if behavior changes, update documentation as well
- if benchmarks or prompts change, state the impact on result comparability
- always distinguish product fixes from methodological changes

### Pull requests or internal handoffs

Each contribution should clarify:

- problem addressed
- solution adopted
- files touched
- residual risks
- verification performed

### Documentation standard

Project documentation is bilingual. When adding strategic documents or manuals, keep:

- an Italian section
- an English section
- a technical and academically suitable tone
